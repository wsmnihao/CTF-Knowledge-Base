# 写作规范

> 本文件定义全书统一的语气、结构、代码与实验格式。
> 每次写章前读一遍，写完按末尾的自检清单过一遍。

## 一、读者假设

- 读者有 Windows / macOS 使用经验，**零 Linux 基础**
- 读者能打开终端，但不知道敲什么
- 每章都要能被「照着敲完」而不是「看完懂了」

## 二、语气

| 要 | 不要 |
|---|---|
| 解释「为什么」 | 罗列参数表 |
| 用类比连接已有认知 | 直接讲术语 |
| 承认取舍与不完美 | 说「很简单」「一看就懂」 |
| 给真实生产环境的坑 | 教科书式理想环境 |
| 说清哪个选项最常用 | 平铺直列所有选项 |

**反面例子**
> `ls -l` 显示文件的详细信息，包含权限、链接数、属主、大小、时间、文件名。

**正面例子**
> `ls -l` 比 `ls` 多给了几列关键信息，其中最该记住的是**第一列**——那串 `drwxr-xr-x`。它是权限位，拆开看：`d` 是目录，`rwx` 是属主权限，`r-x` 是属组权限，最后 `r-x` 是其他人权限。第二个 `x` 对应目录意味着「能进去」，这是下一章权限模型的核心，先记住这个形状。

## 三、章节骨架（固定，不要改）

```markdown
# 第 N 章 标题

> **本章目标**：读完后你能……（1–3 条，具体到可验证的行为）
>
> **前置知识**：第 X 章「章节名」
>
> **预计耗时**：N 分钟

导语段（150–300 字）：为什么现在学这个、它解决什么真实问题。

## N.1 小节标题
## N.2 小节标题
...
## N.x 本章小结
## N.y 动手实验
## N.z 自测题
```

**章节内部节奏**（每章都要有）
1. 引入问题（真实场景，不是定义）
2. 概念建立
3. 命令/操作拆解
4. 常见错误与排查
5. 真实生产场景
6. 小结 → 实验 → 自测

## 四、篇幅规则

| 章类型 | 篇幅 | 交付方式 |
|---|---|---|
| 概念/命令/原理章 | 6000–8000 字 | 一次写完 |
| 综合章 | 8000–12000 字 | 视情况拆两段 |
| 代码密集章（8/14/15/18/20/21/24） | 10000 字+ | **必须拆两段**：先正文主体，第二次补实验+自测 |

拆分时在文件末尾留一行 `<!-- TODO: 实验与自测 -->` 标记进度。

## 五、代码与命令规范

### 5.1 提示符约定

```bash
# 普通用户
user@ubuntu:~$

# root
root@ubuntu:~#

# Debian/Ubuntu 传统 root 提示符
#
```

**提示符本身不输入**，正文里第一次出现时说明一次即可。

### 5.2 代码块类型

- `bash` — 命令、脚本、shell 交互
- `console` — 输出内容（终端回显）
- `text` — 配置片段（但 yaml/json/caddyfile 用对应语言名）
- `json` / `yaml` / `toml` / `ini` / `c` / `sql` — 对应语言高亮

### 5.3 输出格式

命令与它的输出**必须分成两个块**，中间用 `→` 视觉分隔：

````markdown
```bash
$ lsblk --output NAME,SIZE,FSTYPE,MOUNTPOINT
```

```console
NAME   SIZE FSTYPE MOUNTPOINT
sda     20G
├─sda1   1G ext4   /boot
└─sda2  19G ext4   /
```
````

### 5.4 危险操作标记

任何会**删除、覆盖、重启、改网络**的命令，正文首次出现时用 `⚠️` 标注并说明后果：

> ⚠️ `rm -rf /` 不会报错也不会确认，它会立刻执行。养成一个习惯：先敲 `ls` 看清楚要删的是什么。

### 5.5 命令参数取舍

给命令时遵循**「最常用的一个写法 + 说明其他选项何时用」**，不要罗列全部选项表。例外：`chmod`、`find`、`grep` 这类选项极多的命令，值得单独开一段讲最常用的 3–5 个。

### 5.6 注释

代码块内可以用 `#` 注释关键行，但**不注释显而易见的行**。

## 六、实验格式（固定）

```markdown
## N.y 动手实验：<一句话说清做什么>

> 环境：Ubuntu 24.04 LTS，Server 版亦可
> 耗时：约 N 分钟

### 目标
一句话。

### 步骤

1. **第一步做什么**
   ```bash
   具体命令
   ```
   预期输出：
   ```console
   ```
   说明为什么要这么做。

2. **第二步**
   …

### 验证

```bash
# 用来确认实验成功的命令
```

### 思考
1. 如果把 X 改成 Y，会发生什么？
2. …

### 清理
```bash
# 撤销实验留下的改动
```
```

**实验硬性要求**
- 必须能在**纯 Ubuntu 24.04 LTS 干净环境**跑通
- 必须给出预期输出，读者要能自查
- 必须有清理步骤
- 不依赖任何需要付费、需申请、或需连特定靶场的东西
- 必须有「思考」环节，答案不写在正文里

**每章实验数量：1–2 个**

- **一个实验**：`## N.y 动手实验：<标题>`，内部直接是 `### 目标/步骤/验证/思考/清理`。
- **两个实验**：仍在同一个 `## N.y 动手实验` 之下，先加两个 `### 实验 N：<标题>` 作为分组标题，每个分组各自带完整的五段（ch01/ch02/ch03 采用此形式）。
- 无论一个还是两个，`目标/验证/思考/清理` 这四个 `###` 标题都必须**每个实验各出现一次**，不得合并。

## 七、自测题格式（固定）

```markdown
## N.z 自测题

### 一、简答
1. …（5–8 题）

### 二、命令填空
1. `ls -l` 中 `drwxr-xr-x` 的第一列 `d` 表示什么？
   （写出完整命令）

### 三、故障分析
> 现象：…
> 问题：…
> 1. 你按什么顺序排查？
> 2. 最可能的原因是什么？
> 3. …
（3–5 题）

### 四、综合实践
写一段脚本 / 完成一个操作 …
（1–2 题）
```

**配比**：简答 5–12 / 填空 5–14 / 故障分析 3–5 / 综合 1–2。答案全部放附录 C，正文不写答案。

> 题量与章节的核心小节数量和命令密度正相关，不要为凑数硬加，也不要为省事砍掉某个知识点的检查。参照：ch01–ch04（简答 8 / 填空 8–10）、ch05（简答 12 / 填空 14，因为覆盖 11 个小节和 20+ 个命令）。**四类必须齐全是硬要求，具体题数是软范围。**

## 八、写作禁令

1. **不逐字或近似转录任何已出版教材内容**。可以沿用章节主题与知识顺序，所有解释、类比、例子、代码必须原创。
2. **不出现「ReiserFS」「xinetd」「dump/restore」「telnet 服务」等过时内容**，见 `BANNED.md`。
3. **不写「安装 Kali 作为默认环境」**，见 `BANNED.md`。
4. **不使用「注意：/ 提示：」开头然后接一句废话**这种凑字数的写法。
5. **不出现未经验证的具体版本号**。需要提版本时写「Ubuntu 24.04 默认的 X 系列」而不是编一个版本。
6. **不留 TODO 占位**（除代码密集章明确标记的实验段）。
7. **不写「将在后续章节详述」然后真的不写**。
8. **代码块必须能直接复制运行**，不写伪代码冒充可运行代码。

## 十一、交付前自检清单

写完一章，逐条核对：

- [ ] 骨架完整：章节头（含目标/前置/耗时）→ N.1…N.x → 本章小结 → 动手实验 → 自测题
- [ ] 导语是真实场景，不是定义
- [ ] 没有 `BANNED.md` 里的过时内容
- [ ] 所有命令在 Ubuntu 24.04 LTS 下语法正确
- [ ] 危险命令有 ⚠️ 标注和后果说明
- [ ] 命令输出单独一个代码块，用 `console` 类型
- [ ] 实验有：目标 / 步骤 / 预期输出 / 验证 / 思考 / 清理
- [ ] 自测题有四类，配比达标，**正文无答案**
- [ ] 交叉引用的文件名真实存在
- [ ] 没有 TODO 占位（除非是标记好的实验段）
- [ ] 篇幅达标（按第 2 节）
- [ ] `README.md` 状态表已更新
