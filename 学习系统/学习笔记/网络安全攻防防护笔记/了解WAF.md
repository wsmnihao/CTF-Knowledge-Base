# 一、为什么需要WAF
## 1.1、Web安全演化史
### 时间线：防护手段演进
2000年前：网络层防火墙
├─ 只能控制IP和端口
├─ 无法理解HTTP协议
└─ SQL注入、XSS等应用层攻击无法防护

2000-2005年：IPS出现  
├─ 开始分析应用层内容
├─ 但误报率高，性能差
└─ 缺乏针对性防护

2005年后：WAF专门化
├─ 专注Web应用防护
├─ 理解HTTP语义
└─ 针对性防御规则
## 1.2、传统防护的局限性
### 传统防火墙的盲点
#### 网络层盲区
- 允许80/443端口通行
- HTTP/HTTPS流量全部放行
- 无法检测恶意Payload

#### 应用层无力
- 看不懂SQL语句
- 识别不了XSS脚本
- 无法解析JSON/XML攻击

## 1.3、现实威胁驱动
## 催生WAF的重大事件
### SQL注入大爆发（2000年初）
- 大量网站被拖库
- 传统防护完全失效
- 急需应用层防护

### Web 2.0安全挑战（2005年）
- AJAX应用复杂化
- API接口暴露增加
- 攻击面急剧扩大

### 合规性要求（2010年后）
- PCI DSS支付卡标准
- 等级保护2.0
- GDPR数据保护
# 二、核心技术-WAF如何工作
2.1、WAF技术架构
## 核心组件分解
### 流量采集层
- 反向代理接收流量

## 2.2、检测技术演进
## 三代检测技术
### 第一代：基于特征
- 简单正则匹配
- 误报率高
- 容易被绕过

### 第二代：基于语法
- 解析SQL/命令语法
- 理解攻击语义
- 准确性提升

### 第三代：基于行为
- 机器学习模型
- 异常行为检测
- 自适应学习
# 三、部署实践-如何部署WAF
## 3.1、部署模式对比
## 四种部署方式
### 云WAF服务
- 优点：快速部署，无需维护
- 缺点：流量经过第三方
- 代表：Cloudflare, Akamai

### 反向代理模式
- 优点：控制力强，功能完整
- 缺点：单点故障风险
- 代表：ModSecurity + Nginx

### 透明桥接模式
- 优点：网络拓扑不变
- 缺点：配置复杂
- 代表：Imperva

### 主机层WAF
- 优点：深度应用集成
- 缺点：性能影响大
- 代表：WordPress安全插件
## 3.2、规则库管理
### 规则库生态
#### OWASP Core Rule Set
- 开源规则标准
- 持续更新维护
- 行业最佳实践

#### 商业规则库
- 0day快速响应
- 专业化分类
- 厂商技术支持

#### 自定义规则
- 业务特异性防护
- 误报率优化
- 攻击模式适配
# 四、对抗演化-绕过与反绕过
## 4.1、绕过技术体系
### 绕过技术分类
#### 语法变形绕过
- 大小写变异：SeLeCt

#### 编码混淆绕过
- URL编码：%53%45%4C%45%43%54

#### 协议层面绕过
- HTTP参数污染：?id=1&id=2
- 分块传输编码
- 请求包拆分

#### 逻辑层面绕过
- 规则条件触发绕过
- 资源限制绕过
- 规则库版本差异
